# Deployment

Publishing to Google Play and the App Store. For private beta distribution see [EAS.md](EAS.md#7-distribution).

> **Status:** the app has **not** been published to either store. This is the procedure plus the compliance work that must happen first.

---

## 0. Pre-flight — required for both stores

| Item | Status | Notes |
|---|---|---|
| In-app account deletion | ✅ Implemented | Requires migration `0005` applied |
| Privacy policy (public URL) | ❌ **Missing** | Mandatory — the app collects email + study content |
| App icons per platform | ✅ Done | Generated by `scripts/generate-icons.mjs` |
| Bundle identifier | ✅ `com.studiq.app` | Permanent once published |
| Versioning | ✅ | `autoIncrement` on `production` |
| Migrations applied in production Supabase | ⚠️ Verify | `0002`, `0004`, `0005` at minimum |
| Crash reporting | ❌ Not set up | Strongly recommended before a public release |

**Account deletion is not optional.** Apple guideline 5.1.1(v) requires any app that lets you create an account to let you delete it in-app; Google Play requires a deletion path too. This is one of the most common rejection reasons.

## 1. Google Play

### 1.1 Build an AAB

Play requires an Android App Bundle, not an APK. The `production` profile does that:

```bash
npx eas-cli@latest build -p android --profile production
```

### 1.2 Signing

EAS manages the keystore. **Back it up before your first release** — losing it means you can never update the listing again:

```bash
npx eas-cli@latest credentials
```

Alternatively enrol in **Play App Signing**, where Google holds the release key and you keep an upload key. Recommended for long-lived apps.

### 1.3 Versioning

| Field | Where | Behaviour |
|---|---|---|
| `version` ("1.0.0") | `app.json` | User-facing. Bump manually per release |
| `versionCode` | EAS (remote) | Auto-incremented. Must strictly increase |

Play rejects an upload whose `versionCode` is not higher than the last one.

### 1.4 Console setup

Play Console → Create app, then complete:

- **Store listing** — name, short/full description, screenshots (phone required), 512×512 icon, 1024×500 feature graphic
- **Content rating** questionnaire
- **Data safety** — declare email + user content collection, and link the privacy policy
- **Target audience**
- **Privacy policy URL**

### 1.5 Upload

Either upload the `.aab` from the build page manually, or:

```bash
npx eas-cli@latest submit -p android --latest
```

(Automated submission needs a Google Play service-account JSON — see Expo's docs.)

### 1.6 Release tracks

`internal` → `closed` → `open` → `production`. Internal testing reaches testers in minutes and is the right place to start.

## 2. Apple App Store

Requires the **Apple Developer Program — $99/year**. There is no free alternative for store distribution.

### 2.1 Build

```bash
npx eas-cli@latest build -p ios --profile production
```

EAS asks for your Apple ID and manages certificates and provisioning profiles automatically. Use `production` (not `preview`, which is ad-hoc internal distribution and requires registering each device UDID).

### 2.2 Certificates

Handled by EAS. Inspect or reset them with `eas credentials`. If you already manage certificates manually in the Apple Developer portal, EAS can reuse them.

### 2.3 Upload to App Store Connect

```bash
npx eas-cli@latest submit -p ios --latest
```

### 2.4 TestFlight

Once processed (10–30 min), the build appears under **TestFlight**:

- **Internal testers** — up to 100 users on your team, no Apple review, available within minutes
- **External testers** — up to 10,000, requires a short Beta App Review

Testers install the **TestFlight** app, accept your invite, and get Studiq as a normal app. **Builds expire after 90 days.**

### 2.5 App Store review

Submit for review with:

- Screenshots for required device sizes (6.7" and 6.5" iPhone at minimum)
- Description, keywords, support URL, **privacy policy URL**
- **App Privacy** questionnaire — declare email address and user content
- A demo account (reviewers must be able to sign in) — provide credentials in the review notes

Expect 24–48 hours. Common rejection causes for an app like this: missing account deletion (implemented ✅), missing privacy policy (❌ outstanding), or reviewers unable to sign in (always supply a working demo account).

### 2.6 Sign in with Apple

**Not required here.** It's only mandatory when an app offers third-party social login (Google, Facebook…). Studiq uses first-party email/password only. Adding social login later would trigger this requirement.

## 3. Release checklist

```
[ ] npx tsc --noEmit passes
[ ] All three self-checks pass
[ ] Manual smoke test on a physical device
[ ] Migrations applied to the production Supabase project
[ ] Anonymous sign-ins disabled; email confirmation set as intended
[ ] version bumped in app.json
[ ] Everything committed (EAS builds from git)
[ ] npm ci --include=dev passes locally
[ ] Production build created
[ ] Privacy policy live and linked
[ ] Store listing complete
[ ] Demo account ready for reviewers (iOS)
[ ] Keystore backed up outside the repo
[ ] CHANGELOG.md updated, git tag created
```

## 4. Post-release

**Bug fixes** — if JavaScript-only, ship over the air (minutes, no review):

```bash
npx eas-cli@latest update --branch production --message "fix: …"
```

Both stores permit OTA JS updates; they do **not** permit changing the app's purpose or adding features that bypass review.

**Native changes** — new modules, permissions, icons or an SDK upgrade need a full build and resubmission.

**Rollback** — republish a previous update to the branch. There is no instant rollback for binaries; you must submit a new build.
